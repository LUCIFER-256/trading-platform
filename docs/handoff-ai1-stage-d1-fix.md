## Findings (each verified by the auditor; reproduce before fixing)

**F1 (critical, reproduced on real PostgreSQL 16.15 with the project's own migrations):** `PostgresPersistencePort.fromCatalog` selects `p.provider_code` and `i.instrument_code`, but the writer login `platform_market_data` has SELECT only on `providers(id, enabled)`, `instruments(id, market_id, enabled, price_increment, size_increment)`, `markets(id, enabled)`, `provider_instrument_symbols(provider_id, instrument_id, provider_symbol, enabled)` and `market_data_policies`. Your own integration test (`set role platform_market_data`, then `fromCatalog`) fails with `PostgresPersistenceError ... catalog failed. SQLSTATE 42501` (permission denied). The grants are a security decision and are NOT to be widened. A query that uses only the granted columns works (the auditor ran it as the writer): join `provider_instrument_symbols s` to `providers p` (enabled), `instruments i` (enabled), `markets m` (enabled) and `market_data_policies pol` (enabled), selecting `s.provider_id, s.instrument_id, s.provider_symbol`.
Required design: the session's labels (`providerId: "coinbase"`, `instrumentId: "btc"`) are engine configuration, not catalog data. `fromCatalog(database, config)` takes `{ providerLabel, instruments: [{ label, symbol }] }` from the caller, resolves each configured `symbol` to its `instrument_id` and `provider_id` through the granted columns above, and fails with the safe `catalog` error if any configured symbol is missing, disabled, policyless, mapped to more than one provider, or if two labels resolve to the same instrument or one label to two. No code column is ever selected.

**F2 (defect):** `flushIds` is a `Map` that grows by one entry per quality bucket for the life of the process (memory leak in a long-running engine). Required: keep a flush id only until its append succeeds, then delete it; keep it across failures (so a retry after a lost acknowledgement reuses the same UUID and the database does not double count). Prove both behaviors with tests (retry after failure reuses the id; after success the map is empty and a new bucket with the same in-memory flush id gets a different UUID).

**F3 (defect):** `appendObservation` resolves the instrument only from `providerSymbol` and ignores `request.instrumentId`, so a request whose label and symbol disagree is silently stored on the symbol's instrument. Required: resolve both and refuse (safe `catalog` error) unless the label's instrument equals the symbol's instrument.

**F4 (test realism):** the unit test mapping has only the key `btc` and uses `providerSymbol: "btc"`; the integration test uses the symbol `SYNTH-USD` as the instrument id. Neither matches the real session, which sends label `btc` with symbol `BTC-USD`. Required: both suites use label and symbol as the session does (label `btc`, symbol `BTC-USD`; a second instrument label `eth`, symbol `ETH-USD`).
